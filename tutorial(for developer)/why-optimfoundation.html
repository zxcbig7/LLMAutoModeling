為什麼是 OptimFoundation

一個 solver-agnostic 的 MIP 建模框架。核心主張只有一句：讓「定義問題」與「呼叫求解器」徹底解耦——上層只寫變數 / 參數 / 限制式 / 目標式，換 solver 只換引擎，模型程式碼一行不動。這份文件從工程師的角度，拆它底層怎麼做到、為什麼這樣設計。

泛型抽象 反射 + 快取 Roslyn Source Generator Pool API Solver-Agnostic Telemetry LLM-Ready

五個設計撐起這個主張

#技術一句話殺掉的痛點
1EngineBase<TModel,TVar,TExpr,TConstr>四個型別參數把 solver 型別整個抽掉建模 code 與 CPLEX/Gurobi API 黏死
2反射 ModelElementBase + deterministic key物件即變數身份證（ClassName@v1@v2）命名 / 查找 / 對解值散落各處
3VariableBuilder建幾十萬變數名稱不靠反射、不建實例大模型建變數又慢又吃記憶體
4AutoSetsGenerator一行 attribute，編譯期長出整個 class每個變數 / 參數一堆重複樣板
5Pool API + Experiment不移項建約束、可記錄可調參、LLM-ready限制式手抄易錯、調參靠翻 log

1它到底消滅了什麼痛點

直接用 CPLEX / Gurobi 的 .NET API 寫最佳化問題，工程上會撞到四道牆：

建模與 solver 黏死
INumVar、GRBVar、ILinearNumExpr 散落整個專案。換 solver = 重寫。
樣板地獄
每個變數 / 參數都是「宣告欄位 + 建構子 + 組 key」的重複 code。一個排班問題十幾個類別全是噪音。
限制式容易抄錯
右邊有變數要移項、改號、合併同類項。人腦做這個，錯一個符號整個模型不可行，還難 debug。
調參不可累積
比較不同 mipEmphasis 只能人工翻 log、手抄目標值與時間，無法系統化，更不能餵給工具學。

OptimFoundation 把這四件事全部下沉到框架。下面逐一拆它怎麼做到。

2工程核心一：用泛型把 solver 型別整個抽掉

所有共用邏輯（變數管理、Pool、批次建變數、實驗記錄）都在 EngineBase：

EngineBase.cscsharp
public abstract class EngineBase<TModel, TVar, TExpr, TConstr> : ISolverEngine
  • TModel = solver 模型物件（CPLEX Cplex / Gurobi GRBModel）
  • TVar = 變數（INumVar / GRBVar）
  • TExpr = 線性表達式（ILinearNumExpr / GRBLinExpr）
  • TConstr = 限制式（IRange / GRBConstr）

接新 solver 只要實作一份 OptEngine : EngineBase<...>，override 11 個 Solver Contract 抽象方法。框架其餘部分完全不知道底下是誰。

三層繼承text
EngineBase<TModel,TVar,TExpr,TConstr>     ← solver 無關的共用邏輯
   ├── Cplex.OptEngine    : EngineBase<Cplex, INumVar, ILinearNumExpr, IRange>
   ├── Gurobi.OptEngine   : EngineBase<GRBModel, GRBVar, GRBLinExpr, GRBConstr>
   └── Solver.OptEngine   : EngineBase<...>   （自研 solver）
工程價值

solver 差異被收斂到一個 class 的 11 個方法。AddVariables 這種可選 override 還能讓各 solver 用原生 batch API（CPLEX NumVarArray / Gurobi AddVars）一次 interop 建 N 個變數——效能熱點留在該優化的地方，不污染上層。

3工程核心二：物件即變數身份證

所有模型元素都繼承 ModelElementBase。它只做兩件事，卻撐起整個框架的「無樣板」體驗：

DesignBases.cscsharp
public abstract class ModelElementBase
{
    // PropertyInfo[] 快取：反射 GetProperties() 每次 ~100ns，快取後 ~10ns
    private static readonly ConcurrentDictionary<Type, PropertyInfo[]> _propsCache = new();

    // 把 sets 依「property 宣告順序」填值（反射 + 型別轉換）
    public void InitClassBySets(params object[] sets) { /* 數量檢查 + Convert.ChangeType */ }

    // 產生唯一 key：ClassName@val1@val2@...（DateTime 固定 yyyy-MM-dd）
    public override string ToString() { /* 反射讀 props 拼 key */ }
}

於是一個變數類別只剩 properties，零建構子：

VariableB_ShiftAssign.cscsharp
public class VariableB_ShiftAssign : VariableBase
{
    public DateTime Date     { get; set; }
    public string  Employee { get; set; }
    public string  Group    { get; set; }
}

而它的 ToString() 就是它在整個系統裡的唯一識別字串：

variable keytext
VariableB_ShiftAssign@2026-01-01@E1@D
│                     │          │  │
class 名稱            Date        E1 Group
為什麼這個 key 是關鍵設計

它讓「建立變數」和「在限制式裡引用變數」用同一個物件、同一個 key。約束裡寫 new VariableB_ShiftAssign { Date=d, ... }，ToString() 出來的 key 必然對得上建立時的 key——不需手動維護字串、不需 ID 表。

代價與護欄也很清楚（框架列為天條）：

  • property 宣告順序 = key 的 @ 順序，必須與 Build*Vs 傳入順序一致；不一致 → KeyNotFoundException。
  • 類別只能有 properties，多一個成員 InitClassBySets 的數量檢查就炸 ArgumentException。

這是「用約定換掉樣板」的典型取捨——而這兩條紀律正好是 source generator（見 §5）能在編譯期幫你守住的。

4工程核心三：建幾十萬變數還要快

排班、路徑這類問題，變數數量是多個 set 的笛卡爾積，動輒數十萬。VariableBuilder 做了三個明確的效能決策：

(1) 建構子用 Expression.Lambda 編譯成 delegate 後快取，而非每次反射 Activator.CreateInstance：

VariableBuilder.cscsharp
private static readonly ConcurrentDictionary<Type, Func<string[], object>> _ctorCache = new();
// 優先無參數建構子（零建構子設計），向下相容 object[] / string[] 建構子

(2) 笛卡爾積直接 yield return string[]，不做「字串拼接再 Split」的來回。

(3) 熱路徑 GetVarNames<T> 根本不建實例——純拼字串產出所有變數名稱，官方註解標「比舊版快 10x 以上」：

VariableBuilder.cscsharp
public static IEnumerable<string> GetVarNames<TVariable>(object[] sets)
{
    string typeName = typeof(TVariable).Name;
    var stringLists = ConvertSetsToStringLists(sets);
    foreach (var parts in GenVarParts(stringLists))
        yield return typeName + "@" + string.Join("@", parts);
}
一個容易忽略但關鍵的細節

ConvertSetsToStringLists 支援 DateTime/int/long/double/decimal/string/enum 當 set，浮點數一律走 InvariantCulture——確保和 ToString() 的 key 格式逐字一致，否則 build 與 lookup 的 key 對不上。enum 是 value type 無法靠共變比對，特地用非泛型 IEnumerable + 元素型別偵測繞過。

5工程核心四：一行宣告長出整個 class

§3 的「零建構子」已經夠精簡，但連 properties 都還要手寫。AutoSetsGenerator（一個 Incremental Source Generator）把它推到極限——宣告即模型：

宣告式建模（FORM 02）csharp
using OptimFoundation.Modeling;

[OptVar(VarType.Binary, "Date:DateTime", "Employee", "Group")]
public partial class VariableB_ShiftAssign { }   // ← 你只寫這一行

[OptParam("Date:DateTime", "Group")]
public partial class Parameter_ShiftDemand { }    // ← 自動補 set 屬性 + QTY + 建構子

編譯期生成 VariableB_ShiftAssign.AutoSets.g.cs，等價於 §3 的手寫版。幾個值得一看的工程決策：

  • 零組件參考。 attribute 與 VarType enum 用 RegisterPostInitializationOutput 注入到使用端自己的編譯。使用者只要 using OptimFoundation.Modeling;，不需任何 NuGet / 專案參考。
  • 增量、精準觸發。 用 ForAttributeWithMetadataName 而非掃整棵語法樹，只有帶標記的節點進 pipeline。
  • 生成 code 用 global:: 全名指向 OptimFoundation.Core.VariableBase，避免 namespace 衝突。
  • 參數強制 QTY 在最後：一個參數代表「某組 key 下的一個數值」，QTY 排在所有 set 之後——和 §3 反射填值的順序約定對齊。
這一層真正的價值不只是少打字

source generator 是把 §3 那兩條紀律收編的最佳位置。後續可讓它在編譯期直接報錯——沒標 partial、混進非 property 成員、QTY 不在最後、BuildBVs set 數對不上——把原本執行期才炸的例外提前到紅色波浪線。這是框架目前最有發展空間的一塊。

手寫（FORM 01）與宣告式（FORM 02）完全等價、可混用——產出的是 partial class，需要時在另一個同名 partial 補方法即可。

6工程核心五：不准移項的 Pool API

數學限制式翻成 code 最容易錯的地方是「整理式子」。OptimFoundation 直接禁止使用者做這件事，改用 LHS / RHS 雙 Pool：

Constraint_OneGroup.cscsharp
// 每位員工每天只能排一個班別： Σ_g X[d,e,g] = 1
dataload.Group.ForEach(g =>
    engine.AddLHS(1, new VariableB_ShiftAssign { Date = d, Employee = e, Group = g }));
engine.AddRHS(1);
engine.CreateEqual($"OneGroup@{d:yyyy_MM_dd}@{e}");   // 送出後 Pool 自動清空

送出時框架自己算：

框架內部text
(LHS terms − RHS terms)  {sense}  (RHS const − LHS const)

兩邊都能放變數和常數，框架負責移項合併。使用者唯一要守的不變式是：

唯一不變式

AML 數學式左邊的項 → AddLHS；右邊的項 → AddRHS。嚴禁自己移項、改號、化簡、翻轉比較方向。

這把「人腦做代數」這個最大出錯來源從流程裡刪掉了。配合 §3 物件即 key，整個限制式建構變成「照抄數學式」。軟性限制式（CreateLeSoft / GeSoft / EqSoft）也走同一 Pool：違反不報不可行，而是把偏差量乘 penalty 加進目標式，框架依目標方向自動決定懲罰符號。

7工程核心六：可記錄 · 可調參 · 面向 LLM

最後一道牆是「調參不可累積」。框架在 Core 層補了一套 solver-agnostic 的單次求解記錄器：

Trial.Capturecsharp
// 不接管 engine 生命週期，只讀設定 + 跑一次 + 讀指標
Trial t = Trial.Capture(engine, "emphasis=2", () => engine.Solve());
experiment.AddTrial(t);
experiment.Save();   // → experiments/<name>.csv（給人比對）+ .json（給 LLM 學）

它補上兩個原本散落或缺失的抽象面：

  • 統一 telemetry：ISolverEngine.LastMetrics 讓三個 engine 在 Solve() 後各自回填 SolveMetrics（Status / Objective / BestBound / MipGap / WallTime / Node·Iteration count / 收斂軌跡）。取不到的欄位填 null 而非丟例外。
  • 統一可調旋鈕：ITunableConfig 把各家「都有但沒抽象」的旋鈕（Seed / Emphasis / FeasibilityTol / OptimalityTol / RootAlgorithm / Presolve / MemoryLimit）對映成跨引擎共通介面。
net48 相容性陷阱（值得記）

JSON 用 System.Text.Json，但必須綁 8.0.0 而非 8.0.5——net8 消費端的 shared framework 只提供 assembly 8.0.0.0，綁 8.0.5 會在 net8 app 載入失敗。options 開 UnsafeRelaxedJsonEscaping（中文直出）+ AllowNamedFloatingPointLiterals（非 Optimal 的 NaN）。

戰略價值

CSV 給人做 tuning 對照，JSON 是結構化的「設定 → 指標 → 軌跡」，明擺著為 LLM 自動調參鋪路。ITrajectorySource 這個 opt-in hook 本期只 CPLEX 用 MIPInfoCallback 實作，其餘宣告不支援、呼叫端不報錯——典型的「抽象先留好，實作後補」。

8進階：框架沒把上層綁死

這些抽象沒有以犧牲彈性為代價。需要逐行掌控時，框架留了後門：

  • 繼承 OptEngine 可直接拿原生 Model、Variables 字典、ReadVar、SetVarLB/UB，做 dual value 擷取或動態改界限。
  • Benders Decomposition 一級支援：ResetConstraint()（保留變數清約束）、CopyModel()、跨 model 的 Thread 限制式 + MergeModel()。一般限制式 attach 在 model 上不能跨 model，Thread 限制式用 Le/Ge/Eq 建立、暫不屬於任何 model 所以能搬——這個分界是 CPLEX MultipleUseException 逼出來的正確設計。

抽象負責 80% 的日常，後門負責 20% 的硬核需求，兩者不打架。
